# awesome-chat

Личный проект-портфолио. Три репозитория:

- `awesome-chat-backend` — Go, этот репозиторий
- `awesome-chat-frontend` — React + Vite + TS
- `awesome-chat-deploy` — k3d, Vault, манифесты кластера

## Дорожная карта

### Этап 1 (в работе) — инфраструктура и деплой

Ведётся в `awesome-chat-deploy`, состояние там в `STATUS.md`.

Сделано: кластер k3d, Vault в dev-режиме, kubernetes auth с политиками и
ролями на каждый сервис, External Secrets Operator, Reloader. Цепочка
Vault -> ESO -> k8s Secret -> env пода проверена и работает.

Postgres, Redis и MinIO подняты чартами bitnami, пароли из Vault, образы
прибиты по digest. Kafka не разворачиваем: выпиливается в пользу Redis
Streams.

Дальше: Deployment'ы, Job для миграций, Ingress; затем пересоздание Vault
в боевом режиме (init, unseal, персистентность) как отдельное упражнение.

### Этап 2 — репозиторий awesome-chat-proto

Отдельный репозиторий с контрактом: `.proto` со схемами и HTTP-аннотациями
grpc-gateway, buf для генерации. Из одного источника — Go-сервер и, позже,
TypeScript-клиент для фронта.

### Этап 3 — переработка сервисов под контракт

`api` получает `registerGRPC` и `registerHTTP` через grpc-gateway,
регистрация роутов идёт в composition root. `ws-server` остаётся
исключительно websocket-сервером и ходит в `api` grpc-клиентом.

Открытый вопрос по этапу 3: обратный путь рассылки. При нескольких репликах
`ws-server` сообщение, пришедшее в реплику A, должно долететь до клиента на
реплике B. Решается fan-out через Redis: `api` публикует после
сохранения, все реплики подписаны. Тогда sticky-сессии на Ingress не нужны.

## Сборка

docker-compose удалён: эталон деплоя — `m-job-api`, там его нет. Локальный
запуск через `make run`, образы через `make images`.

Один Dockerfile на все бинари из `cmd/`, сервис выбирается на сборке:

    docker build --build-arg SERVICE=api -t awesome-chat/api:dev .

Финальный слой FROM scratch, в образе только бинарь и сертификаты. Отсюда
следствия: нет шелла (отлаживать через `kubectl debug` эфемерным
контейнером), нет `/tmp` (нужен emptyDir в поде, иначе развалится приём
голосовых через `ctx.FormFile`), пользователь задаётся числом 65532.

## Конфигурация

Только переменные окружения, без YAML и без библиотек. Каталог `configs/`
и пакет `loader` удалены вместе с зависимостью cleanenv.

`internal/infrastructure/config/env` — загрузчик на stdlib. Он копит ошибки
вместо падения на первой: забыв три переменные, узнаёшь про все три сразу,
а не за три деплоя. Обязательные значения берутся через `String`/`Int`,
необязательные через `*Default`, пустая строка и пробелы считаются
отсутствием значения.

У каждого компонента свой `NewConfig(l *env.Loader)`, у каждого приложения
свой, собирающий компоненты и возвращающий `l.Err()` одним разом.

`apps.AppEnv` — int8-перечисление, читается из `APP_ENV`. Нулевое значение
`Unknown`, а не `Local`: забытая переменная не должна молча означать
локальную разработку. Валидные значения: local, development, staging,
production.

Локальный запуск: `make run` подхватывает `local.env`. В кластере те же
переменные приходят из ConfigMap и Secret.

Go 1.27 везде: `go.mod` (директива и toolchain), CI, сборочный образ.
golangci-lint ставится сборкой из исходников, иначе релизный бинарь,
собранный старым тулчейном, откажется анализировать модуль.

## Договорённости

Никаких комментариев в коде, особенно на русском. Пояснения — в
документации, а не в исходниках.

Каталоги и пакеты именуются по-гошному: короткое слово в нижнем регистре,
без camelCase и подчёркиваний. Транспортный слой лежит в `internal/transport`.

Все команды, меняющие состояние кластера, набирает пользователь сам:
k3d, helm, kubectl, vault. Это обучение, а не автоматизация. Claude пишет
манифесты и скрипты, объясняет поля и разбирает ошибки по выводу.

В kubeconfig есть рабочие продовые контексты. Перед любой командой,
меняющей состояние, называть ожидаемый контекст.

## Проверки

    go build ./...
    go vet ./...
    go test -race -shuffle=on ./...
    golangci-lint run ./...

Все четыре должны проходить чисто. CI в `.github/workflows/ci.yml`
делает то же самое плюс проверку gofmt и go mod tidy.

## Незакрытое в бэкенде

Аудит и план правок — в памяти проекта (`audit-remediation-plan`).
Коротко, по убыванию важности:

1. Схема БД: миграция 2 не добавляет email и password, потому что
   пересоздаёт таблицы через CREATE TABLE IF NOT EXISTS. Outbox нерабочий:
   нет колонок entity_name и created_at, писатель их не заполняет.
   Неверные имена таблиц: `FROM chat` вместо `chats`, `FROM message`
   вместо `messages`.
2. Авторизации нет ни на одном роуте API. Gin-middleware аутентифицирует
   `uuid.New()` вместо куки. WS-апгрейд доверяет path-параметру.
   `/api/ws/broadcast` и pprof открыты наружу.
3. `chathub`: отправка в закрытый канал, `Shutdown` закрывает каналы под
   живыми продюсерами, `GetClients` возвращает внутреннюю map без
   блокировки, `client.id = userID` конфликтует между вкладками.
4. Redis Stream: consumer ID константа, нет XAUTOCLAIM, инвертированная
   ветка ошибки в `stream/subscriber.go`, дроп сообщений по `default`.
5. Kafka-путь мёртв: consumer и `worker/kafka` осиротели, у порта
   `ws.Broadcaster` ноль реализаций. Решить — оживлять или удалять.
6. Voice: в БД пишется presigned URL с TTL 15 минут вместо object key,
   роут не зарегистрирован, waveform-генератор написан и покрыт тестами,
   но не подключён.
